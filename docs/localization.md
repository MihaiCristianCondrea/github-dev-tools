# Localization

GitHub Dev Tools keeps translatable application copy in feature-oriented JSON resources under `src/locales/`. English is currently the only active language and defines the canonical namespace and key structure that every future locale must reproduce.

## Current status

- Active locale: `en`
- Runtime language switching: not enabled yet
- Canonical resources: `src/locales/en/`
- Localization boundary: `src/core/localization/Localization.ts`
- Validation command: `npm run validate:locales`

Adding another locale directory prepares its resources, but it does not make that language selectable until locale discovery, persistence, and language switching are implemented in the runtime.

## Required structure

Every locale must contain the same four namespace files:

```text
src/locales/
├── README.md
├── en/
│   ├── common.json
│   ├── github-tools.json
│   ├── favorites.json
│   └── leaderboard.json
└── <language-tag>/
    ├── common.json
    ├── github-tools.json
    ├── favorites.json
    └── leaderboard.json
```

Use BCP 47 language tags for directories, such as `ro`, `de`, `pt-BR`, or `zh-CN`.

## Namespace ownership

### `common.json`

App-wide copy shared across features:

- Application title, short title, and description
- Startup and loading states
- Navigation labels
- Theme and settings labels
- Generic actions
- App showcase copy

### `github-tools.json`

Copy for Repo Mapper, Release Stats, Git Patch, and shared GitHub-tool states:

- Form labels and placeholders
- Button states
- Output labels
- Validation messages
- GitHub API errors shown to the user

### `favorites.json`

Copy generated by the favorites feature:

- Empty states
- Quick-access labels
- Remove-repository accessibility descriptions
- Mapper and statistics actions

### `leaderboard.json`

Copy for the leaderboard:

- Search and country filters
- Loading and empty states
- Ranking counts, dates, positions, and pagination
- Location and remote-source errors
- Profile-link accessibility descriptions

## What must be localized

Put text in locale resources when a person can read or hear it through the application. This includes:

- Visible headings, descriptions, labels, buttons, chips, and empty states
- Form labels and user-facing placeholders
- `aria-label`, `aria-label-selected`, `title`, and meaningful `alt` text
- Loading, success, and error messages
- Dynamically generated sentences
- Document title and description
- PWA name, short name, and description

The English metadata values in `index.html` and `public/manifest.webmanifest` are static browser fallbacks. Their canonical values still live in `common.app`, and locale validation requires the copies to stay synchronized.

## What must not be localized

Keep technical or externally supplied values outside locale files:

- Material icon names such as `open_in_new`
- Route IDs, hash paths, DOM IDs, CSS classes, and storage keys
- Repository owners, repository names, release names, tags, asset names, and usernames
- URLs, API paths, access-token examples, and country slugs
- Raw patch contents and generated repository trees
- Internal diagnostics that are logged but replaced by a localized user-facing error

Country display names currently live in English resources, while their stable API slugs remain technical data attributes.

## Using localized copy

### Raw HTML templates

Use escaped `{{namespace.key}}` tokens:

```html
<h2>{{githubTools.home.title}}</h2>
<md-icon-button aria-label="{{common.navigation.openMenu}}"></md-icon-button>
```

`localizeTemplate()` resolves and HTML-escapes these values before the Web Component template is mounted.

### TypeScript-generated UI

Import only from the localization boundary:

```ts
import { formatMessage, strings } from "../../../core/localization/Localization";

removeButton.setAttribute(
  "aria-label",
  formatMessage(strings.favorites.removeRepository, {
    repository: `${favorite.owner}/${favorite.repo}`,
  }),
);
```

Do not import JSON files directly from presentation, domain, or data code. `src/core/localization/Localization.ts` is the only locale import boundary.

### Variables

Use named `{variable}` placeholders:

```json
{
  "removeRepository": "Remove {repository} from favorites"
}
```

Translations must preserve the same placeholder names. Do not assemble sentences by concatenating translated fragments because word order differs between languages.

### Counts and formatting

Use the localization helpers for values presented to users:

```ts
formatEnglishPlural(count, messageOne, messageOther);
formatNumber(downloads);
formatDate(date, { year: "numeric", month: "long", day: "numeric" });
formatOrdinal(rank);
```

The current plural helper is explicitly English-only. Before activating languages with additional plural categories, replace it with locale-aware message selection that supports categories such as `zero`, `few`, and `many`.

## Adding a new string

1. Choose the namespace that owns the copy.
2. Add the key to every locale directory.
3. Reference the key through `strings` or a template token.
4. Preserve named placeholders in every translation.
5. Use complete sentences instead of concatenated fragments.
6. Run `npm run validate:locales`.
7. Run `npm run check` before opening a pull request.

English keys should describe meaning and context rather than repeat the English sentence. Prefer `startupErrorDescription` over a vague key such as `message2`.

## Adding a language

1. Copy `src/locales/en/` to a BCP 47 directory such as `src/locales/ro/`.
2. Translate values only. Keep namespace file names and JSON keys unchanged.
3. Preserve punctuation required by the product and every `{placeholder}` name.
4. Keep product names, GitHub terminology, and technical examples consistent.
5. Run `npm run validate:locales` to detect missing files, unknown keys, empty values, and placeholder mismatches.
6. Add the locale to the runtime only after its resources are complete.
7. Test layouts with longer translations, keyboard navigation, screen readers, number/date formatting, and right-to-left direction when applicable.

## Validation contract

`scripts/validate-locales.mjs` enforces the following:

- `en` exists and all required namespaces are present
- Every locale contains the same keys as English
- Locale leaves are non-empty strings
- Named interpolation placeholders match English
- Raw HTML localization tokens resolve to known keys
- User-facing HTML text and accessibility attributes are not hardcoded
- Common TypeScript UI sinks do not receive hardcoded copy
- Locale JSON is imported only by the localization boundary
- `index.html` and `manifest.webmanifest` metadata matches `common.app`

CI runs `npm run check`, and the Pages workflow validates locales again before building the deployment artifact.

## Translation review checklist

- Read the text in its screen context, not as an isolated dictionary entry.
- Keep button labels concise while preserving intent.
- Verify singular, plural, and ordinal behavior.
- Verify placeholders appear naturally in the translated sentence.
- Avoid inserting HTML into translations.
- Check accessibility labels independently from visible labels.
- Confirm that translated text does not overflow cards, buttons, chips, or the mobile top bar.
